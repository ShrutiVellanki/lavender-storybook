# Development and Contribution Guidelines

This library is a **shared repo with a federated contribution model**. Product engineers add and change components. There is no separate team that implements every request. The contract is tokens, file layout, stories, and tests — not a ticket queue.

---

## How engineers contribute (federated)

Product work stays in the product until it is clearly shared. Then it is extracted here, in the same PR or immediately after, so Finance and Portfolio do not keep a private fork.

**When it belongs here.** It appears in two products, or it is a primitive (Button, Badge) that a product would otherwise reimplement. One-off dashboard chrome stays in the product.

**When it does not.** A single-use layout, a one-off hex, or a variant that exists to dodge the token file.

**What a contribution looks like.**

```
src/components/ui/MyComponent/
├── MyComponent.tsx
├── MyComponent.types.ts
├── MyComponent.styles.ts   # optional
└── index.ts

stories/my-component.stories.tsx
```

| Step | Owner | Done when |
| --- | --- | --- |
| 1. Token | Anyone, reviewed as API | Colour / radius / type uses a semantic name, or a new token is added to `globals.css` for both Dawn and Moon |
| 2. Component | The product engineer who hit the need | Types in `*.types.ts`, no `any`, refs forwarded, `cn()` for classes |
| 3. Stories | Same PR | Playground with controls, one story per state, both themes checked |
| 4. Tests | Same PR | `play` function on Playground; portal cases assert against `document.body` |
| 5. Sidebar group | Same PR | Inputs / Layout / Data Display / Information / Forms / Theme — by job, not by size |

Token changes are shared API. A new `--chart-6` or a radius change is reviewed like a component prop, because every product inherits it.

Forks that never return are the failure mode. Copying a folder into Finance and diverging it is not federated contribution — it is the duplicated implementation this repo exists to stop.

---

## How design + engineering work together

Storybook is the working file. There is no second spec in Figma that code is allowed to drift from. Designers review Playground, Dawn/Moon in the toolbar, and the token pages. Engineers ship the folder + stories.

| Decision | Who | How |
| --- | --- | --- |
| Visual language | Design, encoded as tokens | Primitive vs semantic on **Design Tokens / Overview**. A hex that is not in the file does not ship. |
| Reusable vs custom | Both, using the two-product rule | Two surfaces → extract. One surface → stay in the product. |
| Component API | Engineering | Props in `*.types.ts`. Controlled where the product owns state (Modal `open`). |
| Disagreement | Tokens win | Product wants a one-off chart hex. System wants `--chart-4`. Chart-4 wins, or the extended palette grows. Hardcoding in a component is the old problem. |
| A11y | Engineering, gated in CI | Keyboard and ARIA in the component. `addon-a11y` on every story (`color-contrast`, `label`, `button-name`, ARIA). |

Design does not throw a mock over the wall. Engineering does not invent a fourth button height in a product PR. The shared repo is where those decisions are recorded.
